## 目标与参考

参考本地 `tiaoli` 项目的问题中心，为 Whose.Domains 提供自动错误采集、相同问题聚合、后台排查与处理闭环。首版聚焦用户提出的“收集系统错误”，采用现有 Spring Boot、MySQL 和 Layui 后台，不引入外部错误监控服务。

参考文件：`tiaoli/docs/superpowers/plans/2026-09-18-issue-center.md`、`tiaoli/tiaoli-admin/src/pages/issues/IssuesPage.tsx`。该项目的医疗业务流程、用户反馈和发布操作不直接迁移。

## 用户故事

作为管理员，我希望系统自动记录线上错误，并在问题中心查看发生位置、频率和排查线索，标记处理状态、记录处理备注和修复版本，以便发现与追踪类似域名查询 500 的问题。

## 验收要求

### 1. 自动采集

- 当网站或管理后台出现未处理的服务端异常或 HTTP 5xx 时，系统应记录错误事件，包括应用、环境、时间、规范化接口路径、方法、异常类型和请求 ID。
- 当自有前端出现未捕获 JavaScript 异常、未处理 Promise 拒绝或同源接口请求失败时，系统应自动上报；采集应覆盖 fetch 与项目使用的 jQuery 请求。
- 当域名查询等接口用 HTTP 200 包装系统错误时，系统应通过明确的服务端采集标记记录故障；正常的域名无结果、校验失败、登录过期、权限拒绝和限流不得统一当作系统错误。
- 当已接入的后台任务失败时，系统应记录任务名称及异常；首版接入域名/DNS 刷新、监控与通知任务。具体接入点在设计中列出，不能声称自动覆盖所有 catch 日志。
- 当广告或其他第三方脚本产生无上下文的跨域错误时，系统应过滤，避免淹没自有系统问题。

### 2. 聚合和关联

- 当相同应用、环境、来源、规范化路径和异常特征重复出现时，系统应聚合为同一个问题，更新发生次数及首次/最近发生时间。
- 当同一请求的服务端和前端都报告故障时，系统应依据请求 ID 关联并去重，不重复累加故障次数。
- 当已解决的问题再次发生时，系统应重新打开；已忽略的问题保持忽略并更新统计。
- 当多个事件并发写入时，系统应保证聚合唯一性和计数准确性。

### 3. 后台查看与处理

- 当管理员打开新增的“问题中心”菜单时，系统应展示分页列表，支持按状态、应用、来源、时间和关键词筛选，并标明当前环境。
- 列表应包含问题摘要、来源、发生次数、状态及首次/最近发生时间。
- 当管理员打开详情时，系统应展示分页事件、请求 ID、接口或任务位置，以及经过限制和脱敏的异常类型、调用位置等排查线索；不只显示笼统错误代码。
- 当管理员处理问题时，系统应支持“待处理、处理中、已解决、已忽略”、处理备注和修复版本，并保存操作人及时间。
- 当非管理员访问问题列表、详情或修改接口时，系统应拒绝访问。

### 4. 数据边界与可用性

- 自动事件不得保存密码、Cookie、Authorization、API Key、请求/响应正文或完整查询参数；域名等动态路径参数应规范化。
- 浏览器上报采用允许字段和长度限制；服务端排查线索优先保留异常类和代码栈帧，避免异常消息携带 SQL 参数、凭据或用户输入。
- 上报端点应限制请求大小、事件数量和频率；采集失败不得递归采集自身错误或阻塞业务响应，队列应有上限。
- 测试与正式数据沿用各自数据库隔离；配置应支持关闭采集与声明应用版本。
- 事件明细默认保留 30 天，问题摘要及处理记录默认保留 180 天；定时清理规则应可配置并在设计中明确。

## 首版范围说明

首版不增加用户主动反馈入口、业务流程转化统计、邮件/即时通信告警、截图或录屏。以上是 tiaoli 中可另行扩展的能力，并非本次自动收集系统错误的必需项。

本次开发应提供数据库迁移、实现、回归测试和上线说明；不包含直接修改生产数据库或部署。保留当前工作区已有的域名查询 500 修复。

## 关键验收场景

1. 模拟 `/domain/www.chinabbs.com/search` 服务端异常，后台出现一个可定位的问题，前端报告与其关联，页面退出 Loading。
2. 同类故障重复及并发发生，仅一个问题聚合，计数正确；正常查询无结果不产生问题。
3. 前端异常、接口网络失败和任务异常分别被记录；采集接口本身失败不递归。
4. 状态与备注保存成功，已解决问题复发后重新打开；未授权请求不能读取详情。
5. 上报中包含凭据、正文、超长内容或非法字段时被拒绝或按约定过滤；正常事件仍能记录。
