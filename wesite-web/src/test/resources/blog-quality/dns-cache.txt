===SUMMARY===
Compare cached DNS answers with authoritative data before assuming an update has failed. This guide explains what TTL tells you and which conclusions the comparison cannot support.
===CONTENT===
<h2>Compare answers from the right places</h2>
<p>A resolver can return cached data while an authoritative server holds a different answer. The difference alone does not prove that either service is broken. First identify the exact name and record type you want to investigate. Write both down so that later comparisons refer to the same question. A different record type is a different query, and comparing unrelated answers can hide the actual problem.</p>
<p>Before starting, identify the authoritative server for the zone and the resolver used by the affected application. Use a DNS query tool that lets you choose the destination server. Record the destination, query name, record type, response and observation time. If the application uses another resolver, your diagnostic query may not reproduce what the application sees. Keep that uncertainty visible in your notes.</p>
<ol><li>Query the selected authoritative server for the exact name and type.</li><li>Query the application's resolver for the same name and type.</li><li>Compare the answer records and TTL values, recording when each response was observed.</li><li>Repeat the comparison later to investigate whether the cached answer changes.</li></ol>
<h2>Interpret an illustrative comparison</h2>
<p>Illustrative example, not a live measurement: suppose the authoritative answer contains a new address while the resolver still supplies the previous address. Cached data is one possible explanation. The TTL field describes a caching lifetime in seconds. A zero TTL means that the record is for the current transaction rather than subsequent caching. The record format in <a href="https://www.rfc-editor.org/rfc/rfc1035.html">RFC 1035 section 3.2.1</a> supports that interpretation; it does not promise a universal update deadline across every application.</p>
<h2>Limitations and next checks</h2>
<p>This comparison is a diagnostic observation, not proof that every user receives the same answer. Confirm the selected zone, server and query type before changing configuration. The example does not demonstrate a real outage or establish a tested command sequence. An editor must verify the chosen tool's syntax and the environment-specific procedure before publication. If the answers already match, this particular comparison has not reproduced the reported discrepancy; investigate the actual application's query path instead of claiming that TTL explains every failure.</p>
