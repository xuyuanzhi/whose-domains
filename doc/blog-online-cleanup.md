# 线上博客整理执行清单

适用现状：新版 Admin 已部署；JAR 为 `/usr/java/jar/wesite-admin-1.0.0.jar`，外部配置为 `/usr/java/config/admin/`。

## 第一轮：取得事实清单

1. 确认查重锁和 AI 来源两份迁移已执行；修改文章之前备份 `WEB_BLOG_POST`，记录 Web/Admin 版本。
   先确认部署包包含 `BlogAuditRunner.class` 和 `AdminSchedulingConfiguration.class`，且来自包含完整审计改动的构建。仅显示激活 `blog-audit` profile 不代表旧包具备审计能力；旧包可能照常启动定时任务。新版审计脚本在缺少任一类或 JAR 无法读取时直接拒绝启动。类存在是最低门槛，不替代构建版本和调度隔离校验。
2. 暂停 AI 自动生成任务，整理期间尽量避免同时编辑。审计读取多个批次，持续写入可能让清单与稍后的线上状态不同。
3. 把 `scripts/server/legacy/blog-audit.sh` 上传为 `/usr/java/bin/blog-audit.sh`，执行 `bash /usr/java/bin/blog-audit.sh`。
4. 如果数据库连接、密码、JWT 等环境变量目前写在 `admin-start.sh` 中，先把变量定义原样复制到 `/usr/java/config/admin/runtime.env`，设置文件权限为 `600`。文件只包含变量赋值及必要的 `export`，不要包含 Java 启动、进程检测或停止命令。新版启动和审计脚本会自动加载并导出该文件中的变量；可以通过 `ADMIN_ENV_FILE` 指定其他文件。确认新启动脚本使用共享文件后再移除脚本内重复的变量定义，避免覆盖新值。不要 source 启动脚本，也不要把真实密钥发送给他人。如果没有共享文件，脚本仍支持当前终端已导出的环境变量；仅缺少 `JWT_SECRET` 时会隐藏输入询问。可以通过 `BLOG_AUDIT_CONFIG_DIR` 指向使用数据库只读账号的独立配置目录。
5. 审计以独立 Java 进程运行，使用 `prod,blog-audit` 和非 Web 模式；不需要停止正在运行的 Admin。它额外使用内存和数据库读取资源，安排在低峰执行。
6. 只有退出码为 0 且检测到唯一完成记录时，脚本才生成 `report.json`。只分享这个文件；启动日志可能含环境或连接信息，应留在服务器。

报告列出扫描数量、存在问题的文章 ID/标题/slug/状态、阻断项、提醒及重复匹配；不含正文、流量或外链数据。未列出的文章也不等于事实准确。超过扫描容量时需要另行处理，不能把失败当成没有问题。

## 第二轮：逐篇做决定

取得报告后填写下表，每一组重复内容都需要阅读正文后确认；相似匹配不是可直接批量归档的指令。

| 优先级 | 文章 ID / URL | 问题及匹配文章 | 拟保留 URL | 独有信息待迁移 | 处置建议 | 301 状态 | 人工验证 | 完成状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 待审计 | 待填 | 待填 | 待填 | 待填 | 保留修改 / 归档 / 草稿重写 / 暂不处理 | 待核实 | 待核实 | 未开始 |

- P0：阅读时发现关键事实错误、无法复现的操作步骤或虚构依据，优先修正；严重错误可先撤回。
- P1：已发布文章的相同/高度相似正文及重复标题。结合正文、流量和外链选择保留版本；数据缺失时明确标为待核实。
- P2：值得保留的已发布文章缺少来源、步骤、限制或有内容过薄等问题。第一批选 5–10 篇，逐篇核实并重写。
- P3：草稿及仅标题相似的提醒，先明确选题差异，避免继续产生重复稿。

先记录重复稿的独有信息和旧链接处置，必要时设置 301；归档重复稿后，再修改保留文章。归档保留内容但旧 URL 返回 404，不会自动合并正文或创建跳转。普通撤回仍参加查重，不能替代归档。归档文章恢复后只回到草稿。

## 第三轮：小批次发布与验收

每篇回答一个明确问题，补充可执行步骤和直接支持结论的一手来源，注明适用限制；统一站点署名并保留 AI 来源说明。修改稿先自动检查，再人工核实事实与示例。

每批完成后检查公开页面、内链、署名、旧 URL 和重定向，并再次运行审计。对照相同 ID 的问题变化，记录归档数量，避免把扫描数量减少误认为所有质量问题都已解决。

完整规则、迁移和回滚说明见 [博客查重与内容审查](blog-content-review.md)。本清单不执行线上文章写入；实际处置以审计、正文核实和后台操作记录为准。
