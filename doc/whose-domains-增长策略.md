## 二、收入模型(v2 新增)

> v1 最大的缺口:通篇没有回答"钱从哪来"。一份不知道收入来源的增长策略,其"不做付费墙"不是克制,而是没有模型。

### 2.1 当前现实

**AdSense 是目前唯一的收入来源**。限制已于 2026-07-31 解除,但它依然是**单点且脆弱**的——一次爬虫事件就能再次打断它。这决定了两件事:

- **收入高度集中于单一渠道。** 这既是当前的现金流基础,也是最大的结构性风险,第 2.3 节的演进路径本质上是在为它做分散。
- **广告收入只来自 HTML 页面。** API 返回 JSON,不渲染广告,**API 流量的边际广告收入为零,但边际成本为正**(上游查询、CPU、带宽)。

### 2.2 关键推论:不同流量的单位经济

| 流量类型 | 广告收入 | 成本 | 净值 | 策略 |
|----------|---------|------|------|------|
| 真人访问 HTML 页 | 有 | 低 | **正** | 全力争取 |
| 匿名爬虫抓 HTML 页 | 无(且**污染广告质量**) | 中 | **显著为负** | 必须挡住 |
| 带 key 的 API 调用 | 无 | 中 | 当前为负,**但可转化** | 计量、限额、未来变现 |

中间一行是这次 AdSense 危机的根源——它不只是"不赚钱",而是**主动破坏**真人流量的变现能力。

### 2.3 收入演进路径

1. **现在**:守住 AdSense(唯一收入,限制已解除),同时确保 API 流量不稀释广告质量
2. **6 个月内**:API 超额付费档(定价对标 WhoisXML 的 1/3),把 API 从成本中心转为收入中心
3. **12 个月内**:域名投资人的付费工具(批量监控、WHOIS 变更提醒)——这类用户付费意愿远高于开发者

**判断依据**:第八章的 RPM 指标会告诉你 API 用户到底是资产还是负债,不要凭感觉决定何时收费。

## 三、核心战略:把机器流量从广告页引导到 API(v2 新增)

> 这是 v2 与 v1 最重要的策略差异,也是化解"反爬"与"开放 API"表面矛盾的关键。

### 3.1 矛盾的真相

v1 主张全面开放 API 获客,而 7 月的事件迫使我们把 API 锁紧。两者看似冲突,但真正伤害你的**不是"机器流量"本身,而是"匿名机器流量打在会渲染广告的 HTML 页面上"**:

- 爬虫抓 HTML 页 → 触发广告展示 → 无点击无停留 → 判定无效流量 → **AdSense 被限**
- 同样的数据走 API → 返回 JSON、**不渲染任何广告** → 不产生一次无效展示

### 3.2 策略:分流而非封堵

| 流量 | 处置 |
|------|------|
| 带 key 的 API 调用 | **欢迎**。可计量、可限流、可封禁、可转化为付费 |
| 匿名爬 HTML 工具页 | **挡住**。页面 token + 网段限流 + 广告条件加载(已上线) |
| 真人访问 | 正常体验,正常展示广告 |

**主动引导动作**:在被爬最狠的工具页(WHOIS History、Related Domains、Domain Score)显式放一行:

> *Scraping this page? Use the free API instead — cleaner JSON, higher limits. →*

这一句话把采集者从"广告收入的破坏者"转化为"API 的注册用户"。敌对关系变成获客渠道——**这才是免费 API 对本站真正的战略价值**,v1 只把它当作开发者获客工具,低估了它。

### 3.3 前置条件(不满足则不要开放 API)

1. ✅ AdSense 投放正常(2026-07-31 已确认)
2. 缓存命中率 ≥ 80%(见模块 C)
3. API 返回体已剥离注册人 PII(见 3.4)

### 3.4 合规红线:API 默认不返回注册人 PII

v1 只在风险章节提到"向用户解释查不到注册人是行业现状",但真正的风险是反的:**当前 `/api/domain-report` 会返回注册人 email、电话、技术联系人**。

在 GDPR 下,**页面展示 vs 免费 API 批量分发 PII,法律性质完全不同**——后者本质是在提供个人数据的批量导出服务。

**强制要求**:API 返回体默认剥离注册人 email/phone,只保留机构名、国家等低敏感字段。确有需求走单独申请 + 实名通道。实施成本极低,但能避掉一个真实的合规雷。

## 四、行动模块(按投入产出比重排)

### 模块 A:邮箱注册通道 —— 【最高优先级】(改动量:小,2-3 天)

> v1 把这件事排在第 4 位(模块 D 的一个技术细节),v2 认为**这是全站 ROI 最高的一项**。

**问题**:留存引擎(到期监控)已经完整建好,但入口被一道墙堵死——

- `User` 实体**根本没有 email 字段**(只有 `name`/`phoneNo`/`password`/`vcode`)
- 注册强制走**手机号 + 短信验证码**
- 而 `DomainWatch` 实体里**已经有 `notifyEmail` 字段**

也就是说:**邮箱早已在数据模型里,却要求用户先通过一道短信验证才能填它。** 对一个面向全球开发者和域名投资人的英文站,这是转化率杀手——海外用户不会有中国手机号,短信通道大概率也发不到国外。

**这是当前转化漏斗上最大的一个洞。**

**具体动作**:

1. `User` 表增加 `email` 列(唯一索引),手机号改为可选
2. 增加邮箱注册/登录通道:邮箱 + 密码,或直接 magic link 免密(推荐后者,摩擦最低)
3. 到期监控入口改为:**输入域名 + 邮箱即可添加**,首次添加时自动创建轻量账号并发送 magic link
4. 保留现有手机号通道,不破坏存量用户

**验收标准**:一个海外用户从落地到成功添加第一个监控域名 ≤ 2 分钟,全程不需要手机号。

---

### 模块 B:定位收窄(改动量:小,约 1 周)

**目标**:让访客 3 秒内明白本站与 whois.com 的区别。

1. **首页主标题重写**,突出差异点:*Structured WHOIS & RDAP data for developers — free API, clean JSON*
2. **导航重排**:API Docs 提到导航前列;WHOIS History、Related Domains 等差异化工具前置
3. **降权无关工具**:JSON Formatter、Time Zone Converter 等从首页和主导航移除(**保留 URL 不删,避免损失已有收录**)
4. **页脚版权年份改为动态生成**(当前硬编码 `2025-2026`)

**验收标准**:新访客能复述出"这是给开发者的 WHOIS API 站"。

---

### 模块 C:缓存与容量(改动量:中,约 1 周)—— API 开放的前置条件

> v1 说"单机规模够用",这个判断过于乐观。

**容量现实**:服务器 3.5G 内存、无 swap、web 堆 512M、与另一个 1G 堆的 JVM 共存。按 v1 目标 500 key × 1000 次/天 = **50 万次/天 ≈ 平均 6 QPS,峰值 20-30 QPS**,而每次未命中缓存的 WHOIS 查询是一次到注册局的网络往返(1-3 秒)。**没有高缓存命中率,这个量级会拖垮单机。**

**具体动作**:

1. 热门域名查询结果缓存,**TTL 6-24 小时**(v1 建议的 2-6 小时过短,域名数据变化极慢)
2. 上游多源回退:WHOIS 失败切 RDAP,反之亦然
3. 监控缓存命中率,**≥ 80% 才可进入模块 D**
4. `server.tomcat.max-threads` 从 200 下调至 100-150(200 线程 × 256k 栈 ≈ 50M,对这台机器偏高)

**验收标准**:缓存命中率 ≥ 80%,P95 响应时间 < 500ms。

### 模块 D:免费 API 与 key 体系(改动量:中,1-2 周)

**免费额度设计(v2 调整)**:

| 项目 | v1 建议 | **v2 建议** | 理由 |
|------|---------|------------|------|
| 免费额度 | 1000 次/天 | **100 次/天** | 仍远超 WhoisXML 的 500 次/月(≈17 次/天),传播点照样成立;**额度调高容易,调低会得罪用户** |
| 注册方式 | 邮箱,无信用卡 | 同左(复用模块 A 的邮箱体系) | 拿到邮箱 = 拿到召回渠道 |
| 限流 | key + IP 双层 | 同左(IP 层已实现) | 防滥用 |
| PII | 未提 | **默认剥离注册人 email/phone** | 合规红线,见 3.4 |
| SLA | 尽力而为 | 同左,并**明确保留调整额度的权利** | 单机现实 |

**具体动作**:

1. API key 表 + 每日计数(Redis 计数 + 定时落库),不需要完整用户中心
2. 文档补充:认证方式、curl/Python/JavaScript 三语言可复制示例,目标"5 分钟跑通"
3. **结果页转化位**:每个查询结果角落放 "Get this via API →"
4. **反爬引导位**:被爬最狠的工具页放 3.2 中的引导文案

**验收标准**:陌生开发者从看到文档到拿到第一个 JSON 响应 ≤ 5 分钟。

4. **Hacker News / Reddit(r/webdev、r/devops、r/Domains)**:"Show HN" 或干货帖,重点讲"为什么 WHOIS 纯文本解析很痛苦、RDAP 如何解决"——技术叙事比广告叙事有效
5. **dev.to / 掘金 / V2EX**:教程型文章("用 X 行代码监控域名到期"),文内自然使用自家 API

**期望值修正**:v1 定的"三个月 500 注册"依赖于至少一个渠道跑通,而 Show HN 等渠道的中位数结果是几乎无水花。**把 500 视为乐观情形,150-200 视为基准情形**,不要因为没到 500 就判定策略失败。

---

## 五、流量策略:TLD 程序化 SEO(持续进行)

**现状**:TLD 内容页已实现(`TldContent` 表 + `/domain/{tld}` + `/top-level-domains`)。

**⚠️ 重要修正**:v1 建议 URL 用 `/tld/io`,但**现有实现是 `/domain/{tld}`,已被搜索引擎收录。此时改 URL 结构会损失已有权重,不要改。**

**本阶段重点从"铺页面"转为"填内容"**:

- 先把 30-50 个热门 TLD(.com/.io/.ai/.dev/.app 等)的内容做深:注册规则、注册局、WHOIS/RDAP 政策、价格区间、FAQ 结构化数据
- **纯模板空壳会被判为低质**,这一点在 AdSense 对"程序化生成页面"审查趋严的当下尤其关键
- 与 Blog 配合:每月 2-4 篇 how-to 文章(域名安全、到期抢注、RDAP 科普)

**额外收益**:给核心页面补充人工撰写的说明性内容,同时降低被 AdSense 判定为"低价值批量生成内容"的风险。

## 八、北极星指标与复盘节奏

**三个核心指标**(v1 只有前两个,均为过程指标——一个站可以两项都涨、同时烧穿服务器而收入为零):

1. **监控中的域名总数**——留存与用户价值的代理指标
2. **API key 注册数**——获客与开发者渗透的代理指标
3. **每千次查询毛收入(RPM),分渠道**——**v2 新增**,分开看 HTML 页 AdSense 收入 vs API 边际成本

第 3 项会直接回答:**API 用户到底是资产还是负债**,以及何时该启动付费档。

**辅助指标**:AdSense 展示量与 CTR(恢复监测)、缓存命中率、GA4 中数据中心 IP 占比、提醒邮件打开率、TLD 页自然流量、结果页 → API 注册转化率。

**复盘节奏**:每两周看一次数据;三个月做一次战略复盘。

- 若 API 注册跑赢监控 → 资源向 API 变现倾斜(超额付费档)
- 若监控跑赢 API → 向域名投资人工具倾斜(批量监控、变更提醒),该人群付费意愿更高
- 若 RPM 持续为负 → 收紧免费额度,优先保广告收入

## 九、风险与前提

1. **AdSense 是单点收入,且爬虫事件可能复发**。限制虽已解除,但账号仍在观察期,且引发问题的采集者随时可能换手法回来。**常态化监测**:GA4 中数据中心 IP 占比、AdSense 展示量与 CTR 异常波动、服务器日志中 UA 高度单一的请求。发现苗头立即收紧 Cloudflare WAF 规则。降低这一风险的根本手段是第 2.3 节的收入分散。
2. **稳定性是增长的地基**。开发者把 API 写进生产代码后,一次持续的 502 就可能永久流失。
3. **单机容量是硬约束**。3.5G 内存、无 swap、双 JVM 共存。任何"额度"决策都要先过容量这一关,建议加 2G swap 作为最低成本的稳定性保险。
4. **滥用风险**:免费 API 必然被滥用,key + IP + 网段三层限流,并保留封禁机制(基础设施已就绪)。
5. **合规**:
   - API 默认不分发注册人 PII(3.4 节,红线)
   - 页面上向用户解释"查不到注册人"是 GDPR 下的行业现状而非站点故障
   - 提供数据移除申诉渠道
6. **上游依赖**:注册局 WHOIS/RDAP 限流是常态,缓存 + 多源回退要在架构上预留。
7. **平台政策风险**:AdSense 对程序化生成的大量页面审查本就严格。TLD/工具页必须有真实差异化内容,这是长期的合规成本,不是一次性任务。
